- 画面は管理者と一般ユーザーで完全に隔離する … Q-019（A, 2026-11-05）。`必須（一般）` は一般ユーザーのみ、`必須（管理者）` は管理者のみ通す。`必須` だけの行（`/attendance/{id}`・`/stamp_correction_request/list`・ログアウト・メール認証）は仕様上パスを共有するもので、権限でビューを出し分ける（Q-008・PG12）。
- 【設計判断・2026-11-05 承認】隔離に反するアクセス（例: 管理者が `/attendance` を開く、一般ユーザーが `/admin/staff/list` を開く）は 403 を返す。理由: 相手側の画面は「見られない」ことを明示する。代替案: 各自のトップへリダイレクト（不採用）。※未ログインは従来どおりログイン画面へリダイレクト（`auth` の動き）。
- 【導出】一般ユーザーが通るルートには `auth` に加えて `verified` を付ける（FN011-2: 未認証でログインすると誘導画面へ）。共有ルート（`/attendance/{id}`・`/stamp_correction_request/list`）は管理者も通るので、管理者のシーダーで `email_verified_at` を必ず埋める。
- 【設計判断】`/attendance/{id}` の `{id}` は `whereNumber('id')` で数字に制限する。理由: `/attendance/list`・`/attendance/report` が `{id}` に吸われるのを防ぐ（Q-008 の注記）。代替案: ルートの定義順で回避（順番を入れ替えると壊れるので不採用）。
- 【導出】`/attendance/{id}` は一般ユーザーなら自分の勤怠のみ（FN026「自分の氏名」）。他人の id は 403 を返す（【設計判断】2026-11-04 承認。代替案: 404 で存在自体を隠す）。
- 【設計判断・2026-11-04 承認】`POST /admin/login` は Fortify が自動登録しないため `routes/web.php` に手動で定義し、`Fortify::authenticateUsing` で「`/admin/login` から来たら `admin_status` を確認」する（Q-016）。`/login` から来た管理者も同様に拒否する（Q-021 A）。ログイン後の遷移先も `LoginResponse` で権限ごとに分ける。代替案: 管理者専用の `Admin\LoginController@store`（FN014「fortify」から外れるため不採用）。
- 【設計判断・2026-11-04 承認】`/admin/logout` 後に `/admin/login` へ遷移させるには `LogoutResponse` を差し替える。差し替えないと Fortify の既定で `/` → Q-018 により `/login`（一般用）に着く。仕様書に遷移先の記載は無い。
- コントローラー名 `AttendanceController`・`ApplicationController`・`ReportController`・`Admin\*` は【設計判断】（`AttendanceRecordController@index` のみ [出典: 開発プロセス.md §N+1 問題]）。

**根拠メモ（バリデーション・決定事項）**
- 打刻（`action`）と CSV 出力（`user_id`・`year_month`）には FormRequest を作らない（2026-11-06 ユーザー決定）。理由: 仕様書にエラーメッセージが無く、ユーザーが入力する欄でもないため。
- 表のルールは【出典】【導出】と、open-questions の回答（Q-030 A・Q-031 A・Q-032 A・Q-037 B・Q-038 A, 2026-11-07）で決まったもの。`string` は付けない（HTML フォームからは文字列しか来ず、メッセージも未定義のため）。
- 【回答に基づく文言・2026-11-07】仕様書に無い文言は次のとおりこちらで決めた（Q-030 A・Q-031 A・Q-038 A）。
  - `email.unique`: 「このメールアドレスは既に登録されています」（Q-031）
  - `name.max`: 「お名前は255文字以内で入力してください」、`email.max`: 「メールアドレスは255文字以内で入力してください」、`comment.max`: 「備考は255文字以内で入力してください」（Q-038。API の FN060 の言い方に合わせた）
  - 出勤・退勤の未入力・形式違い（`new_clock_in.required`・`new_clock_in.date_format`・`new_clock_out.date_format`）: 「出勤時間もしくは退勤時間が不適切な値です」（Q-030 ④⑤）
  - 休憩の形式違い・開始と終了の逆転・片方だけの入力・休憩どうしの重なり: 「休憩時間が不適切な値です」（Q-030 ①〜④）
  - Q-037 B（出勤が退勤より後の文言をロールで分ける）は `new_clock_in.before_or_equal` だけに適用する。未入力・形式違いは Q-030 A の文言を一般・管理者で共通に使う。
- 【導出】退勤は空欄可（`nullable`）… Q-032 A（退勤前でも修正できる）。そのため、退勤と比べるルールは退勤が入力されているときだけ動かす（Laravel の `before_or_equal:new_clock_out` は相手が空だと失敗するため、`Rule::when()` などで条件付きにする）。
- 【設計判断・2026-11-07 承認】休憩の「開始と終了は対で入力」は、退勤が入力されているときだけ求める。理由: Q-032 A で休憩中（休憩終了がまだ無い）の当日分も修正できるため。代替案: 常に対で必須（休憩中に修正できなくなる）。
- 休憩どうしの重なりはルールの文字列では書けないので、`withValidator()`（`after()`）で並べて確認する（Q-030 ③）。
- 補足（Q-030 の回答より）: 監修エンジニアの説明では時刻はプルダウンで入力する想定のため、文言の無いケースは基本的に起きない。ただし提供ビューは `type="text"` の入力欄で、リクエストは書き換えて送れるため、サーバー側のチェックは実装する。
- RegisterRequest … [出典: 機能要件一覧.md FN002・FN003 / テストケース一覧.md ID1]。`password_confirmation` の `same:password` は【導出】: FN003-f「確認用パスワードの入力規則違反」＋ views/user/register の `@error('password_confirmation')`。Fortify の登録は CreateNewUser を通るため、FormRequest の当て方は実装で決める（FN002）。→【設計判断・2026-11-22 承認】`CreateNewUser::create()` の中で `new RegisterRequest` の `rules()`・`messages()` を `Validator::make()` に渡す。理由: 上のルート表どおり Fortify の `RegisteredUserController` をそのまま使える。決まりは RegisterRequest の1か所に書ける。代替案: `POST /register` を自作のコントローラーに差し替え、`RegisterRequest` を引数で受け取る（ルート表の変更が要るので不採用）。
- LoginRequest … [出典: FN008・FN009・FN016]。一般・管理者のログインで共用。`email` 形式ルールは付けない【導出】: 形式違いのメッセージが仕様に無く、形式が違えば認証に失敗して「ログイン情報が登録されていません」（FN009-c）が出るため。この文言はルールではなく、認証失敗時に返すもの。
  - 【設計判断・2026-11-22 承認】当て方: `App\Http\Requests\LoginRequest` は Fortify の `LoginRequest` を継承し、FortifyServiceProvider の `register()` で `$this->app->bind(Fortify の LoginRequest, 自作の LoginRequest)` と差し替える。理由: Fortify のログインのコントローラー（ルート表）をそのまま使え、型で受け取る形の FormRequest になる。代替案: RegisterRequest と同じく、認証の処理の中で rules() を呼ぶ（Fortify はログインの入力チェックを先に行うので、二重になる）
  - 【設計判断・2026-11-22 承認】FN009-c の文言の出し方: `config/app.php` の `locale` を `ja` にし、`lang/ja/auth.php` の `failed` に書く。理由: Fortify は認証に失敗すると `trans('auth.failed')` を返す（vendor/laravel/fortify/src/Actions/AttemptToAuthenticate.php で確認）。開発プロセス.md「日本語化は lang/ へのメッセージファイル手動配置で対応」に合う。代替案: `authenticateUsing` の中で自分で ValidationException を投げる（Fortify の失敗の回数の数え方を通らなくなる）
- AttendanceCorrectionRequest … フォーム名は [出典: views/user/user-detail・views/admin/admin-detail の `name=` と `@error`]。比較ルールは [出典: FN029・FN039 / テストケース一覧.md ID11・ID13]。一般・管理者で共用（同一ルート `POST /attendance/{id}`）。クラス名は【設計判断・2026-11-07 承認】。
  - 出勤が退勤より後のときの文言はロールで分ける（Q-037 B）: 一般ユーザーは「出勤時間が不適切な値です」（テストケース ID11）、管理者は「出勤時間もしくは退勤時間が不適切な値です」（FN039・テストケース ID13）。`messages()` 内でログイン中ユーザーの権限を見て切り替える。
  - `new_break_in.*` は「休憩時間が不適切な値です」、`new_break_out.*` は「休憩時間もしくは退勤時間が不適切な値です」、`comment` は「備考を記入してください」 … [出典: FN029・FN039]。
  - 【導出】同じ時刻は可（`before_or_equal` / `after_or_equal`）: 仕様は「より後」「より前」だけをエラーとしているため。
  - 【導出】休憩欄は `nullable`: ビューが末尾に空の休憩欄を必ず1つ出す（FN026）ため、空欄はエラーにしない。
  - `new_date`・`name` は readonly の表示用なので検証しない（日付はルートの勤怠レコードから取る）。
- Api\V1\IndexAttendanceRecordRequest … [出典: API仕様書（応用）.md AP01「すべて nullable」「max:100」/ FN058]。
- Api\V1\StoreAttendanceRecordRequest … [出典: AP03・FN060]。`clock_out`・`comment` の `nullable` は「任意」からの【導出】。unique は2列の組み合わせなので `Rule::unique('attendance_records')->where('user_id', …)` で書く（AP03 の文字列 `unique:attendance_records,date,user_id` をそのまま書くと、3番目が除外IDと解釈されて意図どおりに動かない）。
- Api\V1\UpdateAttendanceRecordRequest … [出典: AP04・FN061（部分更新・`sometimes`・自身を除外）]。
